# fix/process-grouping 改动总结

分支：`fix/process-grouping`（基于 main `86aab7f` / v0.1.4）· 2026-11-20 · 含下表 10 个提交及本篇总结

## 为什么改

v0.1.4 在实际使用里有两类明显问题：

1. **一个软件被拆成很多条。** ChatGPT 等软件每次更新都会换一个带版本号的安装目录（例如 WindowsApps 下的 `OpenAI.Codex_1.2.3.0_x64__…`），而软件身份是按完整路径记的，于是每个版本都成了一个新软件，各记各的。
2. **用户根本没在用的进程也被算成"前台运行"。** NVIDIA Overlay、Razer、BitDock、华硕热插拔这类程序挂着看不见的悬浮窗、停靠栏或隐藏宿主窗口，旧逻辑只要有"可见窗口"就算前台。另一方面，Electron/Chromium 子进程（`--type=renderer` 等）的过滤其实从没生效过，因为进程命令行根本没被读取。

在此基础上，按"从电脑使用者的角度出发"的思路重新定义了什么算在用的软件：**任务栏上有窗口的，或右下角托盘里有图标的才算；其余都是后台进程，不记入软件时长，单独放到新的「后台」页里。**

## 一、识别规则（核心改动）

### 1. 只认任务栏式窗口

新增 `src-tauri/src/window_info.rs`。一个进程只有在拥有「会出现在任务栏 / Alt+Tab 里的顶层窗口」时才算有窗口，判定条件：

- 窗口可见；
- 没有可见的所有者窗口（弹出框、子对话框不单独算）；
- 不是工具窗口 / 不抢焦点窗口（除非显式标了 `APPWINDOW`）；
- 不是鼠标可穿透的叠加层（`LAYERED + TRANSPARENT`）；
- 不是应用自己隐藏（DWM cloaked by app）的窗口；只是被系统隐藏的（例如在别的虚拟桌面上）仍然算；
- 尺寸不为零（最小化的除外）。

UWP 应用的外壳窗口 `ApplicationFrameWindow` 会被归到它真正承载的应用进程上，前台窗口也同样处理；孤立的 `CoreWindow` 忽略。

### 2. Electron / Chromium 子进程

- 现在真正读取进程命令行（每个进程只读一次，只在内存里判断，不存盘）。
- 任何带 `--type=` 参数的子进程都算后台辅助进程，不论进程名叫什么（ChatGPT、Discord 等都适用）。

### 3. 托盘软件（新）

新增 `src-tauri/src/tray_icons.rs`。Windows 11 会在注册表 `HKCU\Control Panel\NotifyIconSettings` 里为每个托盘图标登记一个可执行文件路径。GST 每 30 秒读一次这份名单，并要求：

- 运行中进程的可执行文件与名单匹配（忽略版本号目录，但同一个安装包里的不同 exe 分开，避免把同一安装包里的服务进程当成主程序）；
- 进程在当前用户会话里（服务进程在会话 0，不可能显示托盘图标）。

满足的进程状态为新的「托盘运行」，和前台运行一样建立运行会话、计入运行时长；在软件页上算作窗口外（后台）时长。

局限：

- 注册表会记住"曾经显示过"的图标，所以这是近似判断，偶尔会把现在不再显示托盘图标的程序算进来，可用隐藏列表排除；
- Windows 10 没有这份注册表数据，Win10 上保持原来的判定。

### 4. 状态模型

`AppRuntimeStatus` 现在是四种：前台运行 > 托盘运行 > 后台运行 > 已关闭。同一软件有多个进程时取最高的那个状态。

## 二、软件身份不再随版本拆分

在 `storage.rs` 中，软件身份改为按"与版本无关"的键计算：

- WindowsApps 包：`名称_版本_架构_资源_发布者` 合并为 `名称_发布者`，整个包算一个软件；
- 普通目录：形如 `app-1.2.3`、`v1.2`、带点的版本号目录，以及 12 位以上的十六进制哈希目录，都视为可变部分忽略。

启动时会把旧库里按版本拆开的身份一次性合并到新身份上（可重复执行，结果不变）：

- 每日运行、关注时长相加，单日封顶 24 小时；
- 特别关注 / 隐藏标记一并迁移，冲突时以"隐藏"为准；
- 成员进程迁移，"上次打开"取最晚的一次；
- 显示名保留可执行文件原本的大小写（`ChatGPT` 而不是 `chatgpt`）。

## 三、新增「后台」页

左侧菜单新增「后台」，用来回答"哪些软件在偷偷跑、吃我的电脑"：

- **范围**：既没有任务栏窗口、也没有托盘图标的第三方进程；Windows 系统进程（系统目录下的程序、`System`、`Registry`、`Memory Compression` 等）不列出。
- **归属**：由你正在使用的软件启动的子进程（包括子进程再启动的进程，最多追 16 层）算在那个软件名下，不出现在这里。
- **分组**：同一软件的多个进程合成一行，显示进程数。
- **每行内容**：当前 CPU（占整机的百分比）、内存（运行中显示当前值，已退出显示今日峰值）、今日后台时长、今日 CPU 时间、运行中 / 已退出。
- **排序**：按今天的 CPU 用量从高到低。
- **概况**：顶部显示当前后台软件数、合计 CPU、合计内存。
- **刷新**：每 5 秒刷新一次，窗口不可见时暂停。

数据存储在新表 `daily_background_usage`（按日期 + 软件），记录运行秒数、CPU 核心秒、内存峰值、进程数峰值和最后出现时间。数据库版本因此从 1 升到 2。

概览页相应调整：

- 托盘软件显示绿色「托盘运行」标签；
- 右侧栏从「当前前台运行」改名为「正在运行」，托盘软件也列在里面。

## 四、其他修复

| 问题 | 修复 |
| --- | --- |
| 每次计时只记整秒，丢掉小数部分，日总时长少算 1–6% | 把不足一秒的余量累积到下一次；出现扫描间断时清零 |
| 读取图标前为判断是否 exe 而把整个文件读进内存（Electron 程序 150–200 MB） | 只读文件头 2 个字节 |
| 老式 24 位 / 带遮罩的图标 alpha 全为 0，显示成透明 | 有颜色的像素当不透明处理，全空时退回字母徽标 |
| Tauri 命令跑在 UI 线程上，查询历史、等锁时窗口和托盘会卡住 | 所有命令改为异步，在后台线程执行 |
| 汇总查询对每条会话都做两次文件存在性检查 | 路径相同时直接跳过 |
| 数据库偶发"database is locked" | 两个连接都设置 3 秒忙等待 |
| 某次 panic 会让计时器锁中毒，之后一直停止计时直到重启 | 自动从中毒的锁中恢复 |
| 数据目录或数据库打不开（包括遇到更新版本的库）时直接崩溃 | 改为弹出中文错误提示后退出 |
| 第二次启动 GST 什么也不发生 | 会把已在运行的窗口显示并切到前台；只检查同一个 exe 的窗口，不读取其他程序的窗口标题 |
| 设置读取失败时，默认值会把用户关掉的开机自启又打开 | 读取失败时不同步自启状态 |
| 关闭操作失败时窗口卡住 | 关闭选择对话框里提示「关闭操作失败，请重试。」 |

## 五、隐私

- 仍然不读取窗口标题、文档名、网页标题，也不读取托盘图标的提示文字。
- 新读取的信息：窗口样式和类名、进程命令行（仅在内存中判断 `--type=` 等参数，不保存）、托盘注册表中登记的可执行文件路径。
- 新保存的信息：后台进程的程序名、路径、每日运行时长、CPU 时间、内存峰值和进程数。
- 依然全部存放在本地，没有网络上传、没有遥测。`PRIVACY.md` 已同步更新。

## 六、兼容性与升级

本版本把数据库从版本 1 迁移到版本 2，保留历史事件和心跳记录。旧程序无法打开新版数据库。Windows 10 继续使用窗口识别规则，Windows 11 另外支持托盘图标识别。

## 七、验证情况

- 自动化测试覆盖窗口判定、软件身份合并、计时余量、托盘识别、后台分组、图标、自启同步和后台页面。
- 二次启动唤起窗口、启动错误弹窗以及长期运行的统计准确性仍待手动验证。

## 八、已知未做

- Windows 10 上的托盘识别；
- 每次计时都写一遍软件身份（磁盘写入偏多）；
- 每次轮询都重新传送图标数据；
- 「上次打开」的含义还不够明确；
- 夏令时切换日的边界情况；
- 数据库体积清理（需要先设计好备份方案）；
- 窗口很窄时，后台概况的说明文字略微溢出；
- `ui-v2` 新界面合入时需要移植「后台」页和「托盘运行」状态。
